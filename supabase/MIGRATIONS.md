# Миграции Supabase: как не ловить «Remote migration versions not found»

Проверка **Supabase Preview** в GitHub падает, когда в истории базы
(`supabase_migrations.schema_migrations`) есть версия, для которой нет файла
в `supabase/migrations/`. Версия — это числовой префикс имени файла
(`20260617222530_name.sql` → `20260617222530`).

Так случилось, когда миграции применяли через дашборд или `apply_migration`
(Supabase сам ставит текущее время как версию), а файлы в репозитории
создавали отдельно с другой датой.

## Правило

**Версия файла должна совпадать с версией в базе.** Одно из двух:

1. **Файл первым (рекомендуется).**
   ```bash
   npx supabase migration new add_something   # создаст файл с версией
   # впишите SQL в файл
   npx supabase db push                        # применит и запишет ту же версию
   ```
2. **Применили в базе первым** (дашборд, SQL-редактор, MCP `apply_migration`).
   Сразу после этого создайте файл с **той же версией и именем**, как в базе:
   ```bash
   npx supabase migration list                 # покажет версии базы и локальные
   ```
   Назовите файл `<версия_из_базы>_<имя>.sql` и вставьте туда тот же SQL.

Не переименовывайте и не меняйте даты уже применённых миграций.

## Быстрая проверка перед push

`npx supabase migration list` — в колонках Local и Remote не должно быть
версий, которые есть только в Remote.
